Case study

Modernising the MyHyve Ticketing Portal

Mid-Level Engineer at Hyve Managed Hosting · Sep 2025 - Oct 2026

Angular modernisation, dependency security and cross-stack improvements to a production support application.

  • Angular Initiated the 19 → 21 upgrade and shipped it incrementally, without a rewrite.
  • Security Cut npm audit findings from 50+ to under 5, resolving three of four critical issues.
  • Cross-stack Shipped a support notification preference across Angular, C# and SQL.

Modernising Angular 19 → 21

MyHyve is Hyve's existing Angular and C# ticketing portal. I worked on it within the engineering team; this page covers what I initiated or delivered. It was on Angular 19, but its patterns lagged behind the framework: vulnerabilities kept appearing, and components mixed data access, business rules and presentation. I proposed the upgrade to 21 and implemented it, researching migration paths and package compatibility, then shipping it in steps that kept the application deployable.

The changes that shipped:

  • Angular signals and rxResource in place of manual subscription state and nested observable chains.
  • Modern template syntax and OnPush change detection in components that could support it.
  • API and business logic moved out of large components into services.
  • Related components grouped into feature-oriented directories, with legacy Sass replaced by Tailwind CSS.

OnPush and signals make change detection predictable, services give data access one owner, and feature directories show what a change affects. Most proposed structural changes reached production.

Dependency security

The audit reported more than 50 findings, four critical. I traced vulnerable packages to their transitive dependencies, checked versions against Angular's peer requirements, and added npm overrides. I preserved the shrinkwrap file the deployment depends on and verified the overrides worked with it. That left fewer than five findings, with three of the four critical issues resolved. The rest stayed open; the portal is not vulnerability-free.

Production example: notification preferences

After consulting support engineers, I proposed a role-sensitive notification setting so people could choose which ticket notifications they received. I built the Angular toggle and state, extended the API request and C# endpoint, and changed the SQL schema and query, checking the approach with a backend developer. It shipped with positive feedback from support. The work was outside my frontend specialisation, so I followed existing backend conventions.

Production example: error monitoring

Sentry reported recurring HTTP 400 responses. Some were expected client-side errors, not faults, but the frontend treated them as failures and reported them. I changed the handling to distinguish the two, reducing monitoring noise so the remaining reports were more useful.

Supporting example: monthly ticket automation

An existing automated process misclassified some VM patching orders, so maintenance work went unseen. With Support and Customer Experience, I investigated the cases and agreed a simpler approach: one monthly ticket aggregating the affected orders. I used an AI coding agent for the focused classification patch and submitted it for review; colleagues verified and deployed it.

Engineering approach

Changes went through small GitLab merge requests and colleague review, with manual regression testing. I also prototyped a separate Playwright component-testing build for basic UI components outside the authentication flow; coverage stayed partial.

Outcome

The portal now runs on Angular 21 with fewer than five audit findings. Notification preferences and the error-handling change are in production, and the monthly patch was deployed after review. No usage or performance metrics were recorded.

This case study uses only details that can be stated without internal customer, order or ticket data.
